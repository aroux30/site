## 3. Checkout / Payment Sequence (verified post-fix)

```
UI add-to-cart ── POST /cart/items (optimistic, server response re-syncs)
UI checkout    ── POST /checkout/create-order {cart_id, address_id, shipping_method_id,
                    coupon_code, idempotency_key}
                    1 transaction: cart ownership → line items at LIVE prices →
                    inventory reserve (FOR UPDATE, 30-min TTL) → coupon validate+increment →
                    server shipping + tax → order + item + address snapshots →
                    confirm reservations → cart CONVERTED
                    (checkout_service.py:345-547)
UI payment     ── POST /payments {order_id, provider, amount, idempotency_key}
                    server validates: order owner / PENDING status / amount == order.total
                    (added this audit)
   ├─ zarinpal/idpay/crypto → gateway_url redirect → gateway returns to
   │    /payment/callback/{provider}/{payment_id} (page added this audit)
   │    → POST /payments/{id}/verify (owner-checked, row-locked, added this audit)
   ├─ wallet → in-page: POST /payments → verify → wallet DEBITED in the same
   │    locked transaction that completes the payment (fixed this audit)
   └─ card-to-card → receipt submission → admin approve (payments:manage)
Webhook (server-to-server) ── POST /payments/webhooks/{provider}
   dedup via PaymentWebhookEvent unique(provider, event_id) + row locks;
   NowPayments IPN HMAC enforced fail-closed (fixed this audit)
Verification success → payment COMPLETED → order PENDING→CONFIRMED (FOR UPDATE)
   → outbox events PaymentCompleted / OrderConfirmed published (added this audit)
```

**Unpaid-order recovery (added this audit):** beat cancels PENDING orders older than
`ORDER_PAYMENT_TIMEOUT_MINUTES` (default 60) every 5 minutes, restocks committed
inventory, and writes a status-history row (`orders/application/tasks.py`).

## 5. Where State Belongs (architecture verdict)

- **PostgreSQL** — all business state (catalog, inventory, carts, orders, payments, wallet ledger, coupons, outbox, sessions, audit). Verified: no business state is stored authoritatively anywhere else.
- **Redis** — ephemeral coordination only (rate-limit windows, brute-force counters, IP bans, Celery broker/results, cache). Loss of Redis degrades rate limiting, it does not corrupt commerce state.
- **Elasticsearch** — read/search projection. No write path depends on it; catalog writes never block on ES; ES-down → search returns empty (documented degradation, verified search_service.py:96-108). It cannot become a second source of truth because nothing reads prices/stock from it for transactions.
- **Frontend state** — UX mirrors only. Cart totals are display; checkout recomputes; payment verify is server-authoritative.

## 6. Failure Boundaries (verified behavior)

| Dependency fails | Behavior |
|---|---|
| Elasticsearch | search returns empty; browsing/checkout/payment unaffected (verified) |
| Redis | rate limiting/brute-force degrade; boot continues in dev; liveness unaffected; /readyz reports 503 (accurate) |
| MinIO | media uploads fail; /readyz reports 503; commerce unaffected |
| Payment gateway | create → PaymentError surfaced to UI; verify failure → payment FAILED, order stays PENDING → auto-cancel + restock (fixed) |
| Worker/beat down | notifications/search-sync/outbox drain pause; orders still consistent; outbox retains rows with retries→DLQ (verified outbox_service.py) |
| Postgres down | /readyz 503 (nginx keeps container out of rotation only if configured — see bug matrix INFRA-03) |
