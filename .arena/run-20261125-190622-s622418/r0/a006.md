## 5. 5-Whys Root Cause Analysis

### Problem 1: `form_container` Inspector Controls Starvation
1. **Why were the submit URL, success message, and error message inputs missing when selecting `form_container`?**
   Because the Inspector rendered generic container flex/grid controls instead of the form-specific controls.
2. **Why did the Inspector render generic container controls?**
   Because `renderContentControls()` executed the branch `if (selectedElement.type === "container" && !isSpecializedContainer)` and returned early.
3. **Why was `isSpecializedContainer` false for `form_container`?**
   Because the whitelist array only contained `["nested_tabs", "nested_accordion", "off_canvas", "popup_builder"]`.
4. **Why was `form_container` omitted from this array?**
   It was previously treated as an ordinary layout box during the initial container flexbox overhaul and never updated when dedicated form controls were introduced.
5. **Root Cause Solution**:
   Add `"form_container"` to `isSpecializedContainer` so the switch statement routes directly to `case "form_container":`.

---

### Problem 2: Duplicate Shadow Cases for `toggle` in Canvas and AST Compiler
1. **Why did changes to the second `toggle` case have no effect during testing?**
   Because the TypeScript compiler and Python interpreter evaluated the first match and skipped subsequent cases.
2. **Why did two `toggle` cases exist in both files?**
   During separate development waves (one for accordion/toggle and another for Elementor Pro widget parity), a second case was inserted without refactoring the original.
3. **Why did this introduce latent bugs?**
   The first case in `ast_compiler.py` checked `default_open`, whereas the second case checked `is_open`. AST elements using `is_open: False` stayed opened in SSR because `default_open` defaulted to open.
4. **Root Cause Solution**:
   Remove the dead code cases and consolidate the property resolution into a single, unified handler: `open = is_open if is_open is not None else default_open`.

## 6. SWOT Analysis & TOWS Strategies

### 6.1 SWOT Analysis
- **Strengths (S)**:
  - 100% 4-layer parity for all 13 interactive widgets.
  - Zero TypeScript errors (`tsc --noEmit`), zero Vitest failures, and zero Pytest failures.
  - Native RTL compliance with design tokens and zero raw text leaks.
- **Weaknesses (W)**:
  - Multi-item repeaters (e.g. accordion items, tab items) store shallow JSON arrays in `widgetProps`, which require careful immutable updates.
- **Opportunities (O)**:
  - Extend `form_container` to support client-side schema validation (Zod) before sending payload to `/api/v1/content/forms/submit`.
- **Threats (T)**:
  - Third-party iframe embeds (e.g. Video, Maps) capturing pointer events during canvas drag-drop; resolved by enforcing `pointer-events-none` during editing mode.

### 6.2 TOWS Strategic Matrix
- **SO Strategy**: Leverage full AST and store reactivity to allow instantaneous visual feedback on form inputs and interactive accordion toggles.
- **WO Strategy**: Standardize repeater components across Inspector panels to minimize boilerplate and ensure uniform `data-testid` assignment.
- **ST Strategy**: Maintain strict SVG path sanitization in `html_sanitizer.py` and `ast_compiler.py` to prevent script injection via SVG attributes.
- **WT Strategy**: Enforce automated Playwright sensor audits on every weight progression to catch horizontal overflow and portal z-index regressions.
