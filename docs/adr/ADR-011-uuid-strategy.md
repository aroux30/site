# ADR-011: UUIDv4 for Primary Keys

**Date:** 2026-09-09

**Status:** Accepted

## Context

Choosing a primary key strategy affects database performance, API design, security, and system integration. The main candidates are:

1. **Auto-incrementing integers.** Simple and space-efficient but expose record counts, enable enumeration attacks, and create conflicts when merging data from multiple sources.
2. **UUIDv4 (random).** Universally unique, non-sequential, and suitable for distributed generation. However, random UUIDs cause B-tree index fragmentation and page splits in PostgreSQL because insertions are not ordered.
3. **UUIDv7 (time-ordered).** A newer UUID format (RFC 9562) that embeds a timestamp, providing both uniqueness and chronological ordering. This reduces index fragmentation compared to UUIDv4. However, UUIDv7 is relatively new and has limited library and tooling support.

## Decision

We will use **UUIDv4** as the primary key for all database tables, prioritizing **compatibility and ecosystem maturity** over the index performance advantages of UUIDv7.

### Rationale

1. **Universal library support.** UUIDv4 is supported natively by Python (`uuid.uuid4()`), PostgreSQL (`gen_random_uuid()`), SQLAlchemy, and every client library and tool in our stack. UUIDv7 requires third-party libraries (e.g., `uuid7`) and may not be recognized by all tools.

2. **No enumeration attacks.** Random UUIDs do not reveal record counts, creation order, or growth rate. This is important for user-facing entity IDs in URLs and APIs.

3. **Distributed generation.** UUIDs can be generated by the application layer without database coordination, enabling future scenarios where IDs must be assigned before database insertion (e.g., optimistic client-side ID generation, event sourcing).

4. **Sufficient performance at our scale.** The index fragmentation disadvantage of UUIDv4 compared to UUIDv7 is measurable but not impactful at our projected data volumes (millions of rows, not billions). PostgreSQL's BRIN indexes, table partitioning, and periodic `REINDEX` operations can mitigate fragmentation if it becomes a concern.

5. **Migration path.** If UUIDv7 ecosystem support matures sufficiently, migrating from UUIDv4 to UUIDv7 for new records is straightforward — both are 128-bit UUIDs stored in the same PostgreSQL `uuid` column type. Existing records do not need to be migrated.

## Consequences

### Positive

- No enumeration attacks or information leakage through primary keys.
- Application-layer ID generation without database round-trips.
- Full compatibility with all libraries, ORMs, and tools in the ecosystem.
- UUID column type in PostgreSQL is a compact 16-byte storage, more efficient than string representations.
- Simple, well-understood technology with decades of production use.

### Negative

- Random UUIDs cause B-tree index fragmentation and higher write amplification compared to sequential keys or UUIDv7.
- UUIDs are larger (16 bytes) than integers (4-8 bytes), increasing index size and join costs.
- UUIDs are less human-friendly than integers for debugging, logging, and manual database queries.
- UUIDv4 provides no temporal ordering; queries that need "most recently created" must rely on a separate `created_at` timestamp column.

### Mitigations

- All tables include indexed `created_at` and `updated_at` timestamp columns for temporal queries, eliminating the need for key-based ordering.
- We monitor PostgreSQL index bloat and schedule `REINDEX` operations during maintenance windows if fragmentation becomes measurable.
- For high-write tables that show performance degradation, we evaluate table partitioning by time range to keep index sizes manageable.
- Short UUID representations (e.g., base62-encoded) are used in user-facing URLs where readability matters, while the database stores the native 16-byte UUID.
