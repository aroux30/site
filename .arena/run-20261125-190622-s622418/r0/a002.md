## Executive Summary & Architectural Overview

This deliverable establishes 100% 4-layer parity for all interactive widgets and form controls in the Visual Page Builder (Weight 2). The audited and hardened widget suite comprises 13 core interactive types: `form_container`, `form_input`, `form_select`, `form_textarea`, `form_checkbox`, `accordion`, `tabs`, `countdown`, `nested_tabs`, `nested_accordion`, `toggle`, `popup_builder`, and `off_canvas`. ## 4. Analytical Documentation

### 4.1 5-Whys Root Cause Analysis

**Core Defect**: SSR output discrepancy for container-based structural widgets (`nested_tabs`, `nested_accordion`, `off_canvas`, and `popup_builder`) when rendered through `ast_compiler.py`.

1. **Why did SSR output lack interactive tab navigation pills and drawer wrappers?**
   Because `ast_compiler.py` classified elements solely by `el.type == "container"`, delegating execution directly to `_compile_container()` which treats all containers as generic `<section>` wrappers.
2. **Why was the widget type branch inside `_compile_widget()` not reached?**
   In `block-registry.ts`, `nested_tabs`, `nested_accordion`, `off_canvas`, and `popup_builder` are intentionally instantiated with `type: "container"` to allow dropping child elements into their slots. Therefore, `_compile_element` never routed them to `_compile_widget()`.
3. **Why did the conditional check `if el.widget_type in ("nested_tabs", "nested_accordion") and not el.children` fail for normal trees?**
   Because functional nested tabs and accordions always have child container elements populated by `createDefaultElement()`, causing `not el.children` to evaluate to `false` and bypassing widget formatting.
4. **Why was `toggle` rendered inconsistently?**
   `ast_compiler.py` contained two duplicate branches for `widget_type == "toggle"` (line 1004 and line 1214). The first branch checked `default_open`, while the block registry and second branch used `open` and `is_open`.
5. **Root Cause Solution**:
   - Introduce `_compile_container_widget()` in `ast_compiler.py` to compile specialized container-based widgets with their structural headers, navigation pills, and overlay wrappers while recursively compiling child containers.
   - Unify boolean open state evaluation (`default_open ?? open ?? is_open`) across frontend store, canvas element, and backend compiler.

### 4.2 SWOT Analysis & TOWS Strategies

#### SWOT Matrix
- **Strengths (S)**:
  - 100% 4-layer parity covering all 13 interactive and form widgets.
  - Complete elimination of raw text icon leaks and invalid CSS expressions.
  - Fully responsive, token-driven design system (`bg-card`, `text-primary`, `border-border`).
  - Strict compliance with Persian typography and RTL layout conventions.
- **Weaknesses (W)**:
  - Complex nesting in container widgets requires recursive child compilation and active tab index synchronization.
- **Opportunities (O)**:
  - Seamless extension of Elementor Pro compatibility patterns into lightweight React/SSR modules.
  - Integration of client-side form validation hooks into pre-compiled SSR forms.
- **Threats (T)**:
  - Unsanitized user inputs in custom CSS classes or URLs threatening markup integrity. Addressed via `html.escape` and `nh3` sanitization.

#### TOWS Strategies
- **SO Strategy**: Leverage typed schema definitions in Layer 1 to drive automatic test generation and runtime schema validation in both Vitest and Playwright.
- **WO Strategy**: Abstract repeating multi-item controls (accordion items, tab panes, options lists) into a standardized `ItemRepeaterControl` subcomponent.
- **ST Strategy**: Enforce strict server-side escaping and sanitization in `ast_compiler.py` regardless of client-side validation state.
- **WT Strategy**: Isolate container-widget child state inside `builder-store.ts` to prevent desynchronization between iframe canvas and SSR DOM trees.

| Risk Factor | Probability | Impact | Mitigation Strategy | Verification Sensor |
|:---|:---:|:---:|:---|:---:|
