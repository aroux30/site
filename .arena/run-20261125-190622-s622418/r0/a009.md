## 2. Inspector Controls & State Flow Wiring

### 2.1 Content Tab Wiring
- **Atomic Property Propagation**: When a user updates any widget property (e.g., `label`, `name`, `options`, `submit_url`, or `target_date`), the handler invokes `updateElementProps(selectedElement.id, { [key]: value })`.
- **Zustand Immutability**: All AST modifications clone the node path immutably via `updateElementInTree`, append the previous state to the undo history, mark `isDirty = true`, and increment `mutationVersion`.
- **Options Normalization**: Handlers for `form_select` and `form_radio` automatically parse newline-delimited or comma-delimited strings into clean string arrays while safely supporting object arrays (`{ label, value }`).

### 2.2 Style Tab Wiring
- **Design Token Compatibility**: All color inputs sanitize raw strings into valid HEX codes (`toValidHexColor`) or preserved CSS variables (`normalizeCssColor`).
- **Responsive Layout Spacing**: Padding and margin boxes enforce 4-way linked editing (`isLinked: true`) or independent side overrides across Mobile, Tablet, and Desktop breakpoints.
- **Glassmorphism & Shape Dividers**: Backdrop blur filters (`sm`, `md`, `lg`, `xl`) and SVG shape dividers (`waves`, `curve`, `triangle`, `tilt`) propagate cleanly to `ResponsiveStyles`.

### 2.3 Advanced Tab Wiring
- **Auth Visibility**: Dropdown values (`all`, `authenticated`, `guest`) persist to `element.authVisibility` and compile to SSR attributes (`data-auth="..."`).
- **Custom CSS Classes & Identifiers**: Custom class names and IDs are validated against injection patterns and bound to root elements.
- **Z-Index & Position Controls**: Position modes (`static`, `relative`, `absolute`, `sticky`) and numeric Z-index values are validated and applied directly to the element style tree.

## 5. Analytical Documentation

### 5.1 5-Whys Root Cause Analysis

**Core Problem**: Intermittent form option dropping and canvas selection deadlocks in interactive widgets.

1. **Why did selecting a form input in the canvas occasionally fail to open the Inspector?**
   The native `<input>` element captured the click event, triggering input focus instead of bubbling to the builder element's selection handler.
2. **Why was the click event captured by the input?**
   The canvas iframe did not disable pointer events on form inputs in studio edit mode.
3. **Why were pointer events enabled on editable elements inside the canvas?**
   The canvas element rendered the exact same interactive DOM tree for both edit mode and preview mode without gating interactive controls.
4. **Why was preview mode state not isolated from edit mode?**
   Initial implementations focused on WYSIWYG visual parity, overlooking the distinction between designer selection interaction and end-user form entry.
5. **Root Cause Solution**: Added `pointer-events-none` and `readOnly` / `disabled` attributes to canvas form inputs when `previewMode === false`, re-enabling them when `previewMode === true`.

- **WT Strategy**: Reconcile countdown timers against server response headers rather than relying solely on local client time.
